# SPEC_chimp_hal.md — HAL для Chimp (Banana Pi M64): владение, контракт, фазы

**Создан:** 2026-08-30. **Решение по размещению принято владельцем:** 2026-08-31
(см. §3 — передано через hubd, роль `hv`, от `orchestrator`).
**Статус:** проект, к исполнению. Фаза 0 — ворота, без неё остальное не начинать.
**Цель:** Banana Pi BPI-M64 (Allwinner A64), гость FreeBSD 15.1 arm64 под bare-metal
EL2-гипервизором bzdOS.

**Отменяет для банана:** `docs/CHIMP-READINESS.md` §4 — написан до появления гипервизора
и описывает гостевой HAL как владельца железа.
**Не отменяет:** `docs/specs/SPEC_woodpecker_hal.md` — PinePhone/oBzdOS, там гость и есть
система. Контракт команд оттуда переиспользуется, модель владения — нет.

**Про слово «HAL».** Оно занято гостевой стороной: `bsdOS/hal/` (`bzfb`, `bzkms`, `lima`,
`mali_uio`) — реальные драйверы конкретных устройств. EL2 дважды осознанно отказался
называться HAL: `soc_a64.h:21` («It is not a HAL and it does not abstract anything…
nothing here is selected at runtime») и `RELEASE-0.0.2.md:474` («Deliberately a pure
consolidation, not a HAL»), проверено побайтовой идентичностью бинаря. В этом документе
EL2 везде называется EL2, не «HAL-ядром» — более ранняя редакция (2026-08-30) вводила
термин `halcore`, он снят.

---

## 0. Зачем этот документ

`sys-daemon-zig/` — гостевой демон bsdOS, транспорт `/var/run/bsdos-hal.sock` — **ни разу
не запускался на плате** и спроектирован под модель, которой на Chimp не существует: он
открывает `/dev/iic0`, `/dev/gpio0`, читает sysctl'ы, то есть считает себя владельцем
железа. На Chimp железом реального времени и большей частью периферии владеет EL2.

Два вопроса, на которые нужно было ответить прежде, чем писать в этот демон хоть строку:

1. **Кто владеет каждым устройством** — гость или EL2 (§2).
2. **Где живёт код, обслуживающий железо** — в госте, в EL2, или на отдельном ядре под
   RTOS (§3).

Второй вопрос закрыт решением владельца 2026-08-31: **в EL2, отдельного RTOS-ядра не
заводим.** Остаток документа проектирует то, что из этого следует.

## 2. Правило владения

> **Устройством владеет EL2, если оно (а) нужно EL2 для собственной живучести,
> (б) разделяется с ядрами EL2, или (в) даёт возможность выключить либо
> переконфигурировать то, чем владеет EL2. Всё остальное отдаётся целиком гостю.**

Промежуточных состояний нет: устройство не может быть «наполовину гостевым». Два
драйвера в одном блоке — ровно тот класс аварий, что уже стоил проекту времени
(PC5, PLL_CPUX). После решения §3 у правила больше нет третьего кандидата («HAL-ядро») —
только EL2 или гость.

| Подсистема | Владелец | Почему |
|---|---|---|
| Scanout / дисплей | **EL2** | держит для fbdump и собственной диагностики; гость видит через `bzkms` |
| GPU Mali-400 | **гость** | EL2 не использует; `hal/lima` работает |
| eMMC, EMAC | **EL2** | живучесть: корень и отладочный канал |
| Таймеры, GIC, PLL_CPUX / DVFS | **EL2** | разделяются с ядрами EL2; подтверждено удалением cpufreq |
| PMIC AXP803 (RSB) — чтение и запись | **EL2** | уже реализовано (`axp803.c`+`rsb.c`); гостевой `axp8xx` — прямой кандидат в конфликт владения за тот же RSB |
| Thermal (THS) | **EL2** | политика throttle требует владельца PLL_CPUX; чтение и решение — в одном месте |
| Watchdog — арминг и пинок | **EL2** | зависший гость не должен уметь разоружить watchdog платы; кормление — задача с WCET-бюджетом, не гостевой цикл |
| GPIO | **EL2**, гостю — по allow-list | пинмукс делит блок с eMMC/EMAC |
| DMA-контроллер (`dma-controller@1c02000`) | **EL2** | нет SMMU на A64 (`docs/dma-bypass-stage2.md:177` — «hardware fact, not a software gap»); кто программирует движок — пишет в любую физическую память в обход stage-2 |
| Аудиокодек + DAI (`dai@1c22c00`) | **EL2** | единственный узел с property `dmas` — без него DMA-контроллер не возвращается в строй; гость получает готовый PCM-ring, не регистры (§5) |
| VPU Cedrus | **гость** | не разделяется с EL2, DMA не требует (проверить при реализации, см. §11) |
| I2C / TWI | **нет** | на M64 потребителей нет; не строить |

### Следствие: чтение и действие разделены

Читать состояние может кто угодно. **Действовать** по нему может только владелец. Для
устройств, разделяющих ресурс с EL2 (PLL_CPUX, RSB, DMA), гость не получает даже
альтернативного пути чтения через собственный драйвер — он получает согласованный снимок
через общую страницу (§5), потому что параллельный гостевой драйвер того же блока — это
и есть конфликт владения, а не альтернативный источник правды.

## 3. Решение: EL2 остаётся владельцем реального времени и железа

**Принято владельцем 2026-08-31.** Отдельное RTOS-ядро (Zephyr на выделенном A53) —
отклонено как целевая архитектура. Три причины, все по фактам §1, не по предположению:

1. **EL2 уже является RTOS.** `sched.h:3` — «fixed-priority PREEMPTIVE scheduler for
   the bzdOS EL2 microkernel»: 8 задач (`SCHED_MAX_TASKS`), строгие приоритеты,
   наследование (`sched_set_priority`), статическая память, «fixed, small, deterministic
   bounds». `sched.c:104` — `g_cpu_current[SMP_MAX_CPUS]`, RUNNING-задача пер-ядерная.
   `wcet.h` — период и бюджет на каждый релиз задачи в микросекундах, раздельные
   BUDGET-overrun и DEADLINE-miss, страховочный tick-hook, результат в DRAM-breadcrumb
   `0x50005400 "WCET"`, переживает watchdog-ресет, читается по сетевому REPL. Заводить
   вторую RTOS рядом с уже работающей — не архитектурное решение, а дублирование.
2. **Ядро резервировать не нужно, и это уже отгружено.** При `HCR_EL2.IMO=1` физические
   IRQ уходят в EL2 безусловно, «regardless of the running EL1 context's own `PSTATE.I`
   mask» (`vcpu1.h`). CPU1 при этом отдан гостю третьим vCPU (`VCPU1=1`), а кик watchdog и
   один ограниченный `dbgmon_service()` продолжают висеть на тике этого же ядра,
   GIC-приоритетно вытесняя гостя, — реальное время EL2 не требует посвящённого ядра, оно
   вплетено в существующий тик-механизм на любом ядре, где EL2 в данный момент исполняется.
3. **Zephyr-гость не даёт лучшего детерминизма, только худший.** Он сам требует ядро по
   построению и сам вытесняется трапами EL2 — его детерминизм всё равно ограничен сверху
   поведением EL2. А цена реальна и посчитана: `mmio_absorb.h` не даёт Zephyr-цели вообще
   никакого MMIO passthrough (IPA `0x0-0x7FFFFFFF` целиком невалиден в её stage-2), значит
   любой драйвер, перенесённый туда, всё равно нуждается в НОВОЙ обвязке на стороне EL2 —
   плата дважды за один результат.

Побочный факт, закрывающий прежнюю тревогу этого документа: конфликт CPU3 2026-08-27
(«Zephyr-путь dual-сборки» vs 4-й vCPU) — это **не** рантайм-гонка, требующая выбора
ядра. `vcpu3.c` и `zguest_cpu3.c` оба определяют один не-weak символ `bzdos_cpu3_owner`
(weak-фолбэк — `vgicd.c:159`); собрать оба в один образ — ошибка компоновщика
`multiple definition`, не сюрприз на плате. Цена гипотетического «Zephyr на CPU3» была бы
равна цене всего 4-го vCPU FreeBSD целиком. Шторм 2026-08-27 починен по существу
коммитом `4931822` (маршрутизация data abort'ов по владельцу CPU3); `dbg_vcpu3`
(`vcpu3.c:48`) — рантайм-флаг владения ядром, не заглушка над причиной. CPU3 однозначно
занят гостевым vCPU; вопрос «какое ядро отдать RTOS» больше не стоит, потому что RTOS не
заводится.

### Когда пересматривать

> Zephyr на отдельном ядре возвращается в рассмотрение только если появится (а) жёсткий
> реалтайм-потребитель **вне доверия EL2** (то есть код, который принципиально нельзя
> пускать в TCB гипервизора), или (б) нужда в экосистеме RTOS, которой у EL2 нет и не
> будет — Bluetooth-контроллер, CAN, TSN. Ни того, ни другого сегодня на Chimp нет.

### Что взамен «где живёт HAL»: порт-слой + таблица владения

Вопрос размещения снят, но остаётся другой: как не дать SoC-специфике A64 просочиться в
общий код EL2 и не дать владению устройством стать неявным. Механизм — три шага,
все compile-time, **все в репозитории микроядра** (`<microkernel-repo>/`),
не в `bsdOS`:

1. **`board_bpi_m64.h`** — сейчас не существует, хотя `soc_a64.h` его называет и
   описывает границу SoC/плата: адрес загрузки `0x42000000` и окно DRAM (в `link.ld` /
   `stage2.h`), регистровое знание AXP803, номера GIC SPI, допущение HDMI-стока. Критерий
   приёмки такой же, как у `soc_a64.h`: побайтово идентичный бинарь до и после выделения
   файла — это чистый рефакторинг границы, не новая логика.
2. **Классы владения в `board-config.xml`** — он уже декларативная правда платы
   (`<cpu-roles>`, `<features>`, `<devices>`, `<soc-nodes>`). Добавить классы `hv` (EL2
   держит, гость не видит), `none` (выключено, не мапится, флипать запрещено) и
   `hv-rt` (реалтайм-задача EL2, **без колонки «ядро»** — период/бюджет/приоритет из §3.2
   планируются `sched.c`, где физически исполнится итерация, не архитектурно важно), плюс
   атрибут `shares="phy0"` для разделяемых блоков. Сегодня `FORBIDDEN_DTB_NODES` —
   хардкод-сет в `gen_config.py:68`, а причина запрета живёт прозой в комментарии
   `board-config.xml` — например, `usb@1c1a000` запрещён гостю потому, что PHY0 — тот же
   кремний, на котором сидит MUSB, break-glass-канал EL2; это знание нигде не проверяется
   машиной. С классами и `shares=` запрет **выводится**: узел недоступен гостю тогда и
   только тогда, когда делит блок с `hv`-владельцем. Столбец «Conflict risk» в
   `docs/guest-hw-enablement.md` превращается из прозы в проверяемое условие.
3. **Enforcement — линкер**, той же идиомой, что уже есть в дереве: один не-weak маркер
   на владеемый блок, как `bzdos_cpu3_owner`. Двойное владение = ошибка сборки, а не
   сюрприз на плате без консоли.

Эти три шага — работа в репозитории микроядра, вне доступа этой сессии (см. §11). Ниже,
в §5–§8, документируется бсdOS-сторона: как гость получает данные и действует, при уже
принятом решении «EL2 владеет».

## 4. Контракт: постоянный, независимо от деталей продюсера на стороне EL2

Размещение внутри EL2 больше не варьируется, но **как именно** там формируются данные
(прямое чтение регистра в обработчике, или WCET-задача в `sched.c`, обслуживающая THS раз
в секунду) — деталь реализации EL2, которая тоже не должна протекать наружу.

> **Контракт `/var/run/bsdos-hal.sock` (`CMD ARG\n` → `+OK/-ERR\n`) не знает, кто и как
> заполнил общую страницу (§5) на стороне EL2 — только что она есть и подписана `CAPS`.**

```
        ┌─────────────────── контракт (неизменен) ───────────────────┐
        │ /var/run/bsdos-hal.sock   CMD ARG\n → +OK …\n / -ERR …\n   │
        └───────────────────────────▲────────────────────────────────┘
                                    │ sysctl
                          ┌─────────┴─────────┐
                          │  hal/bzhv (гость) │   тонкий шим, §6
                          └─────────▲─────────┘
                                    │ RO-страница + ioctl
                          ┌─────────┴─────────┐
                          │  hv-статус §5     │  ← интерфейс публикации
                          └─────────▲─────────┘
                                    │ пишет EL2: WCET-задача (термика,
                                    │ фаза 2) → позже питание/watchdog (фаза 3)
```

## 5. Общая страница (`hvstat.h`)

4 KiB, trapped, **read-only для гостя**. Пишет только EL2. Именование и стиль — по
образцу существующего `scanout.h`: функциональное имя, не «hal».

Little-endian. Группы выровнены по 64 байта (cache line Cortex-A53) по правилу Zig/HAL из
CLAUDE.md.

```
off    size  имя                      семантика
--- заголовок ---
0x000   4    HV_R_MAGIC               0x425A4856 ('BZHV')
0x004   4    HV_R_VERSION             версия layout, начинается с 1
0x008   4    HV_R_SEQ                 seqlock; нечётное = EL2 пишет
0x00C   4    HV_R_CAPS                какие группы реально заполняются
0x010   8    HV_R_STAMP               CNTPCT последнего обновления
0x018   4    (резерв)
0x01C   4    (резерв)
--- термика, cache line 1 ---
0x040   4    HV_R_TEMP_SOC_MC         милиградусы C; INT32_MIN = невалидно
0x044   4    HV_R_TEMP_GPU_MC
0x048   4    HV_R_TEMP_MAX_MC         максимум по зонам
0x04C   4    HV_R_THROTTLE_STATE      0 нет · 1 мягкий · 2 жёсткий · 3 критический
--- питание, cache line 2 ---
0x080   4    HV_R_BAT_MV
0x084   4    HV_R_BAT_PERCENT         0..100
0x088   4    HV_R_BAT_CURRENT_MA      знаковое; + = заряд
0x08C   4    HV_R_POWER_FLAGS         b0 ac_present · b1 charging · b2 battery_present
--- живучесть, cache line 3 ---
0x0C0   4    HV_R_WDOG_TIMEOUT_S      0 = разоружён
0x0C4   4    HV_R_WDOG_LAST_PET_S
0x0C8   4    HV_R_GUEST_FAULTS        суммарно (per-core счётчики уже есть в el2_exc.c)
0x0CC   4    HV_R_RESET_REASON
```

Поле-продюсер (`HAL_R_PRODUCER` в прежней редакции) убрано: подмены производителя больше
не будет (§3), различать её не для чего. Если условие пересмотра из §3 когда-нибудь
сработает, поле возвращается тем же однострочным изменением — версия layout (`HV_R_VERSION`)
для этого и существует.

### `HV_R_CAPS` — почему обязателен

Бит выставлен ⇒ группа действительно заполняется. Бит снят ⇒ данных нет.

> **Заглушек, возвращающих правдоподобные значения, не существует.**

Старый контракт (`SPEC_woodpecker_hal.md` §2) предусматривал `get_battery → stub (50%)`.
Это хуже отсутствия: потребитель не отличает «батарея наполовину» от «мы не знаем».
Отсутствующая возможность отвечает `-ERR unsupported`. На M64 неизвестно, подключена ли
батарея физически (§11), — `CAPS` решает это в рантайме.

### Чтение (seqlock, без блокировок)

```
do {
    s1 = HV_R_SEQ;              /* acquire */
    if (s1 & 1) continue;       /* EL2 пишет */
    <читаем нужные поля>
    s2 = HV_R_SEQ;               /* acquire */
} while (s1 != s2);
```

Писатель один (EL2), читателей много — блокировка не нужна ни с одной стороны, тот же
принцип, что и в остальном проекте: **лок = боль**, согласованность через
детерминированный протокол (ср. `[[coordination-free-barriers]]`).

## 6. `hal/bzhv` — шим в госте

Минимальный char-драйвер FreeBSD рядом с `bzkms`/`bzfb`, в том же стиле — реальный
драйвер конкретного устройства (общей страницы EL2), а не абстракция.

**Чтение:** мапит страницу, публикует `dev.bzhv.0.*` — по sysctl на поле, плюс `caps`.
Обновление по запросу sysctl; страница уже в памяти, периодический тред не заводить.

**Запись:** приватный ioctl — паттерн, уже применённый в `bzfb`.

```c
struct bzhv_req {
    uint32_t cmd;      /* BZHV_CMD_* */
    uint32_t arg0;
    uint32_t arg1;
    uint32_t status;   /* out: 0 = ok */
    uint64_t result;   /* out */
};

#define BZHV_CMD_WDOG_PET       1
#define BZHV_CMD_WDOG_ARM       2   /* arg0 = timeout, c */
#define BZHV_CMD_THROTTLE_HINT  3   /* arg0 = уровень; EL2 вправе отказать */
#define BZHV_CMD_POWEROFF       4
#define BZHV_CMD_REBOOT         5
```

Ioctl, а не «дверной звонок» регистром: гостевое ядро сохраняет сериализацию, у вызова
есть возвращаемое значение. `THROTTLE_HINT` называется hint намеренно — решение остаётся
за EL2, владельцем PLL_CPUX (§2).

**Единый механизм чтения — sysctl.** И гостевые драйверы (аудио, lima), и `bzhv` отдают
данные через sysctl-дерево. Демон `bsdos-hal` не мапит память сам, не открывает ioctl для
чтения и не получает нового транспорта — существующая comptime-модель `sys-daemon-zig`
сохраняется целиком.

## 7. Контракт HAL-демона (`sys-daemon-zig`)

**Транспорт:** `/var/run/bsdos-hal.sock`, AF_UNIX, строка на запрос.

**Разрешение противоречия в протоколе.** `SPEC_woodpecker_hal.md` §2 объявляет запрос как
JSON (`{"cmd":"get_battery"}`), CLAUDE.md запрещает JSON в control-plane и требует
`CMD ARG\n` → `+OK\n`, а `main.zig` фактически принимает голый текст и отвечает JSON. Три
источника, три версии. **Канон — CLAUDE.md:** запрос `CMD ARG\n`, ответ
`+OK <payload>\n` / `-ERR <причина>\n`. JSON-ответы `main.zig` переводятся на эту форму;
`SPEC_woodpecker_hal.md` §2 помечается устаревшим в этой части.

| Команда | Источник | Владелец |
|---|---|---|
| `get_uptime`, `get_hostname`, `get_memory`, `get_cpu_usage` | sysctl гостя | гость |
| `get_temperature` | `dev.bzhv.0.temp_*` | EL2 |
| `get_throttle` | `dev.bzhv.0.throttle_state` | EL2 |
| `get_battery`, `get_charging` | `dev.bzhv.0.bat_*`, гейт по `CAPS` | EL2 |
| `wdog_pet`, `wdog_arm`, `throttle_hint` | ioctl `bzhv` | EL2 |
| `hal_version` | comptime | — |
| `get_orientation`, `get_compass`, `get_proximity`, `get_location`, `sms_*`, `get_sim_status`, `haptic` | — | **отсутствуют:** `-ERR unsupported` |
| `set_backlight` | — | **отсутствует:** на M64 панели нет |

## 8. `platform.zig`: `has_X` → `owner_X`

Булев флаг отвечает «есть ли железо». Нужен ответ на «кто им владеет». Один новый enum,
comptime, без рантайм-стоимости. После §3 у него ровно два содержательных значения на
Chimp — `guest` и `el2` — третий вариант (отдельное RTOS-ядро) снят.

```zig
pub const Owner = enum { none, guest, el2 };

pub const owner_thermal: Owner = switch (current) {
    .bpi_m64   => .el2,
    .pinephone => .guest,     // oBzdOS: гипервизора нет, система владеет железом
    else       => .none,      // QEMU
};

/// Совместимость: существующие `has_*` остаются производными.
pub const has_thermal: bool = owner_thermal != .none;
```

### Флаги, которые надо исправить сразу

| Флаг | Сейчас | Должно | Почему |
|---|---|---|---|
| `has_battery` (`platform.zig:87`) | `== .pinephone` → на M64 false | `owner_battery = .el2`, наличие — через `CAPS` | AXP803 на плате есть и уже реализован в EL2 |
| `has_backlight` (`platform.zig:145`) | `bpi_m64 or pinephone` → true | `.none` для `bpi_m64` | панели нет, HDMI |
| `has_i2c` (`platform.zig:133`) | true для M64 | `.none` для `bpi_m64` | потребителей нет; TWI гостю не отдаётся |
| `has_audio` (`platform.zig:139`) | true для M64 | `owner_audio = .el2` (DAI+DMA целиком у EL2, §9 фаза 5) | `audio_bridge.zig` целится в RT5640 (PinePhone), не в кодек A64; и владение иное, чем считалось |

## 9. Фазы

Каждая заканчивается проверяемым результатом; go/no-go стоит там, где решает судьбу
остатка, — по дисциплине, уже применённой в `internal-note`/`internal-note`.

### Фаза 0 — ворота (часы). Без неё дальше не идти

Единственный вопрос: **что гость реально видит.** Запускать на плате, вывод коммитить в
`docs/CHIMP-GUEST-INVENTORY.md`.

```sh
#!/bin/sh
# Фаза 0. Запускать на chimp-guest-freebsd. Ничего не меняет. НЕ ПРОГОНЯН на железе —
# написан по документации FreeBSD и содержимому этого репозитория.
echo "== ncpu/arch =="    ; sysctl -n hw.ncpu hw.machine_arch kern.osrelease
echo "== драйверы A64 ==" ; dmesg | grep -Ei 'aw_|axp|allwinner|ths|gpio|iic|sunxi'
echo "== термика =="      ; sysctl -a 2>/dev/null | grep -Ei 'temperature|thermal'
echo "== питание =="      ; sysctl -a 2>/dev/null | grep -Ei 'axp|battery|acpi\.ac'
echo "== dvfs =="         ; sysctl -a 2>/dev/null | grep -E 'dev\.cpu\.[0-9]+\.(freq|freq_levels)'
echo "== устройства ==" ; ls /dev/iic* /dev/gpioc* /dev/dsp* /dev/fido /dev/dri/* 2>&1
echo "== watchdog =="     ; sysctl -a 2>/dev/null | grep -i watchdog
echo "== звук =="         ; ls /boot/kernel/snd_*.ko 2>&1 | head
echo "== virtio-sound =="; kldstat -v 2>/dev/null | grep -i virtio; ls /boot/kernel/ | grep -i vtsnd
```

Если гостевой `axp8xx`/`aw_thermal` действительно что-то видят напрямую (а не только
через будущий `bzhv`) — это сигнал прямого конфликта владения RSB с EL2 (§2), а не повод
использовать оба источника: конфликт устраняется на стороне порт-слоя (§3.3, `board-config.xml`),
не здесь.

### Фаза 1 — честные флаги (дни, железо не нужно)

`owner_*` из §8; исправление четырёх флагов; вычистка PinePhone-предположений из веток
`bpi_m64`; перевод ответов на `+OK/-ERR` (§7).

Заодно чинится дефект диспетчера: `main.zig:575-619` разбирает команды через
`std.mem.indexOf` (подстрока), а не точным сравнением — команда срабатывает от вхождения
где угодно в строке, порядок проверок значим. Заменить на разбор первого токена.

**Результат:** `bsdos-hal` собирается под `-Dplatform=bpi_m64` и не заявляет ничего, чего
на плате нет.

### Фаза 2 — цепочка целиком на самом дешёвом датчике (недели)

THS → EL2 (первое реальное применение `wcet.c` — периодическая задача с объявленным
период/бюджетом, а не спорадический обработчик) → `hvstat.h` → `bzhv` → sysctl →
`get_temperature`.

Термика выбрана первой не по важности, а потому что она **только для чтения**: проверяет
всю цепочку, ничем не рискуя, и даёт `wcet.c` первого настоящего потребителя — сейчас
модуль существует, но не вызывается нигде.

Ожидать тот же класс грабель с тактированием, что уже был на GPU (`ccu_a64
AW_CLK_HAS_GATE` — гейт не открывался).

**Go/no-go:** `get_temperature` отдаёт значение, меняющееся под нагрузкой, и в
`wcet`-журнале нет deadline-miss на этой задаче. Если цепочка не сходится здесь — не
сойдётся ни на чём дальше.

### Фаза 3 — питание, watchdog, throttle (недели)

Публикация уже реализованного AXP803/RSB в `hvstat.h`; `CAPS`-гейт батареи; watchdog +
`wdog_pet` как WCET-задача EL2 (не гостевой цикл); политика throttle с `throttle_hint` из
гостя. Путь записи (`bzhv` ioctl) впервые появляется здесь.

### Фаза 4 — портирование границы SoC/плата (недели, в репозитории микроядра)

**Не в `bsdOS`.** Выполняется в `<microkernel-repo>/`. Три шага из §3.3:
`board_bpi_m64.h`, классы `hv`/`none`/`hv-rt` в `board-config.xml`, линкер-энфорсмент по
образцу `bzdos_cpu3_owner`. Попутно чинятся две устаревшие записи `board-config.xml`
(`<cpu id="3">` — «never armed», `<cpu id="1">` — «debug-watchdog»), см. §11 п.2 —
хорошая первая проверка, что таблице владения можно верить.

**Go/no-go:** `soc_a64.h`-критерий — побайтово идентичный бинарь до/после выделения
`board_bpi_m64.h`; новый узел, запрещённый гостю правилом `shares=`, ловится линкером на
сборке, а не человеком на ревью.

### Фаза 5 — аудио (недели, первый `hv-rt`-потребитель помимо термики)

По `internal-note`, но со скорректированным блокером: **не тайминги, а DMA.** Аудио-путь
требует `dai@1c22c00` — единственного узла со свойством `dmas`, через который
`dma-controller@1c02000` возвращается в строй. На A64 нет SMMU
(`docs/dma-bypass-stage2.md:177`), поэтому программирующий этот движок пишет в любую
физическую память в обход stage-2: DAI и DMA-контроллер берёт EL2 целиком, гость их не
видит вообще (остаются `disabled` в DTB и в списке запрещённых узлов, §3.3;
черновой `STAGE2_DENY_DMA_CTRL` можно включать уже сейчас, пока в госте некому хотеть DMA).

Форма — та же, что у `scanout.h` («the SAME shape as vblk_emmc.h's»): общий PCM-ring в
DRAM гостя плюс doorbell. Каденцию доливки держит `wcet`-объявленная задача EL2; джиттер
гостя не имеет значения, пока он держится впереди ринга.

**Открытый вопрос, не додумывать:** есть ли в FreeBSD 15.1 драйвер `virtio-sound` — если
нет, это четвёртый модуль в `bsdOS/hal/` (проверяется фазой 0, добавлено в скрипт §9
Фаза 0).

**Go/no-go:** один слышимый тон через ring+doorbell. `audio_bridge.zig` не
переиспользовать: он про RT5640.

### Фаза 6 — VPU Cedrus (недели, независимо, опционально)

По `internal-note`. Владение (гость, §2) предполагает отсутствие разделения с EL2 и
отсутствие потребности в DMA — **это предположение не проверено фазой 0 и должно быть
подтверждено до начала**, тем же вопросом, что закрыл аудио: у какого узла DTB есть
`dmas`. **Go/no-go: один декодированный кадр.** От lima не переносится ничего, кроме
метода и уроков про тактирование.

### Параллельно, вне HAL

Компоновщик поверх готового `/dev/dri/card1` (`internal-note`, `internal-note`, блокер —
`internal-note`) ничем из этого не заблокирован: ядерная часть закончена и измерена, Mesa
упакована.

## 11. Открытые вопросы

Ничего из этого я не проверял на плате: доступ идёт через ноду `workstation`
(LAN 192.0.2.2), с buildhost она недостижима — по карте ресурса входящий TCP на `workstation`
закрыт. Микроядро лежит на `workstation` в `<microkernel-repo>/`, на buildhost его нет.

1. **Что гость реально видит из `aw_thermal` / `axp8xx` / `aw_gpio`.** Закрывается
   фазой 0.
2. **Стилевой долг вне этого репозитория:** `board-config.xml` на `workstation` содержит две
   устаревшие записи (`<cpu id="3">` «never armed», `<cpu id="1">` «debug-watchdog») —
   правится в фазе 4, не здесь; отмечено для передачи роли `hv`/оркестратору.
3. **Есть ли у EL2 место под ещё одну trapped-страницу (`hvstat.h`)** и по какому адресу
   — по образцу `scanout.h`. Не то же самое, что «MMIO для Zephyr» (это закрыто:
   `mmio_absorb.h` подтверждает отсутствие passthrough для RTOS-цели) — вопрос про
   собственную IPA-карту EL2 для нового устройства.
4. **Подключена ли к M64 батарея физически.** AXP803 реализован в EL2, разъём на плате —
   вопрос к владельцу. От этого зависит бит `CAPS`.
5. **Владение VPU Cedrus (§9 фаза 6) не подтверждено** — предположение «гость» верно
   только если у `video-codec@1c0e000` нет своего DMA-узла; не проверено.
6. **Есть ли в FreeBSD 15.1 драйвер `virtio-sound`** — определяет, нужен ли четвёртый
   модуль в `hal/` для фазы 5.
7. **Скрипт фазы 0 не запускался** на живой системе.
